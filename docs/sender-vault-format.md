# Sender vault v1 — bounded browser recovery slice

Status: implemented bounded browser slice; experimental, not native interoperability approval. Verified with Node round trips and real Edge reload/import/continuation tests.

## State and scope

One immutable sender request per vault/backup, at most 20 local entries and 4 MiB total encoded envelope characters (browser quota may be lower). Writes use a same-origin Web Lock to serialize sender tabs; quota or conflict failures revoke the newly created request before publishing invitations. Backup IDs are immutable: differing ciphertext for the same ID fails instead of overwriting. Each has its own random vault ID and independent 24-word English BIP39 phrase (256-bit WebCrypto CSPRNG entropy, @scure/bip39). No shared mutable active-vault pointer; another sender tab cannot overwrite an existing entry. Request creation credentials are NOT persisted. Restore resumes an existing request, not creation authority. Recipient tabs do not open sender storage.

Encrypted plaintext JSON: `{version: "pdfcraft-sender-state-v1", origin, sender}`. `sender` contains every field returned by prepareRequest: approval protocol version, relay ID, admin capability, full manifest including document hash/routing/fields, original PDF encoded as canonical base64, and all invitations (request/recipient IDs, manifest hash, document key, response key, read and response capabilities). No selection drafts or cached polling results. Responses/accepted state are re-read from the authoritative relay and cryptographically validated before continuation; final PDF is reconstructed locally. The backup holds the original PDF, but NOT returned approvals. It cannot reconstruct missing, revoked, expired or lost ephemeral relay requests, and UI must say so rather than claim recovered completion.

## Envelope (exact keys, versioned)

`{version: "pdfcraft-sender-vault-v1", id: <UUID>, kdf: "HKDF-SHA-256-BIP39-entropy", salt: <base64 32 bytes>, nonce: <base64 12 bytes>, ciphertext: <base64 GCM ciphertext including 128-bit tag>}`.

Derive a non-extractable AES-256-GCM key using WebCrypto HKDF-SHA-256 from the 32 entropy bytes obtained by validating the 24-word English BIP39 mnemonic, random 32-byte salt, UTF-8 info `pdfcraft-sender-vault-v1`. This is a high-entropy recovery phrase, NOT a human password or BIP39 wallet seed. No optional BIP39 passphrase. Never derive encryption keys from short verification codes. Fresh nonce and salt per envelope. AES-GCM AAD is UTF-8 JSON.stringify of `[version,id,kdf,salt]` in exactly that order. Base64 is standard padded canonical encoding. Unknown versions/algorithms/extra envelope keys fail closed.

Decoded plaintext max 512 KiB, encoded backup max 1 MiB, original PDF max 180000 bytes; max 12 invitations matching manifest, canonical 32-byte encryption keys and independent capability formats. Validate document digest, manifest binding, IDs and PDF field geometry before accepting restoration. No compression or arbitrary remote resources.

## Persistence and unlock boundary

Store only the encrypted envelope in localStorage under `pdfcraft.sender-vault.v1.<id>`. Phrase and derived key are never persisted alongside it, in cookies/sessionStorage, URLs, relay traffic or logs. Phrase input/display is cleared after successful save/unlock; reload discards in-memory keys. Explicit phrase entry plus local ciphertext or imported backup is required to resume. Export is a download of the SAME encrypted envelope, not a plaintext JSON dump. Restore checks embedded origin equals the current relay origin before any credential-bearing fetch (no automatic origin redirection). A new port requires an explicit future migration contract, not silent capability forwarding.

This protects a locked ciphertext-only backup/storage theft under the high-entropy phrase assumption. It does not protect against malicious hosted JS/extensions, an unlocked browser/process, keylogging, screenshots, weak device security, backups containing both phrase and ciphertext, or deletion/rollback of localStorage. No OS-keystore claim. Clearing browser storage loses local recovery without an exported backup. Keep phrase separately offline and export each request; anyone holding both can recover access. No key rotation, QR/print kit, multi-request aggregate vault, cloud sync or long-term retention promise. The separately configured [durable local relay](durable-local-relay.md) can retain encrypted responses across same-origin restarts; it does not change this backup format.

If storage enumeration throws (including the localStorage getter SecurityError), setup capability processing still runs and an actionable storage warning is shown. New-request publication always requires ciphertext persistence; failures revoke the newly created relay request before exposing links (failed cleanup must be retried). This is not weakened by recovery mode.

For a valid backup plus phrase, recovery first validates state and checks the live relay. If local persistence fails, the decrypted sender state is retained only in memory pending an explicit **Resume session-only** choice. No invitations are published before that opt-in; the phrase input is cleared even on failed/rejected attempts. Retry does not discard the pending state. Session opt-in rechecks the relay and allows existing-request response collection/finalisation and encrypted export, without storing plaintext or keys. Status and export messaging retain the session-only warning. Reload/close requires importing the backup and entering the phrase again; beforeunload requests a warning for pending/session-only state, but browser shutdown/crash/mobile termination can bypass it. Keep the original encrypted backup and separate phrase; no guaranteed memory erasure or crash recovery. To retry persistent import after enabling storage/freeing space, reload and import again.

## Verification

`npm test`: Node coverage includes complete state equality, sequential continuation, wrong phrase, short code rejection, every envelope-field tamper, extra/unknown envelope fields, origin mismatch, malformed/oversized state, bounded storage, non-overwrite conflicts and expiry. RED runs observed missing vault module, missing state validation and missing persistence before implementation.

`npm run test:vault`: real headless Edge first-request phrase setup, encrypted local persistence/export, reload lock/unlock, exact invitation reconstruction, empty-profile import, wrong-phrase refusal, sequential continuation and final-PDF download, missing-request refusal, all-browser-context request AND response URL/header/body plus console checks for mnemonic, document keys and response keys (raw, percent/form-encoded, base64/base64url and key hex forms), second sender isolation and injected quota-error orphan revocation. New strict RED→GREEN regressions observed startup setup lost on getter SecurityError, missing explicit session-only recovery, and a rejected retry retaining the phrase. Tests now cover getter SecurityError and setItem QuotaExceededError during valid imported-backup recovery, explicit opt-in, retained pending state, cleared phrase, navigation-warning handler, finalisation/export, zero session/local storage for quota recovery, and getter-denied creation revocation. No screenshots/traces of recovery secrets are generated. Initial browser RED observed missing recovery UI. The quota denial is deliberately injected; HTTP creation/revocation are real. No physical mobile or security-audit claim.

`npm run test:browser`, `npm run test:ux`, `npm run test:routing`: existing full document/response encryption, PDF rendering/selection races, routing intent races, automatic/manual polling and lost-acceptance-ACK regressions still pass. Existing browser fixtures now acknowledge recovery setup before request creation rather than bypassing it.

Native secure key storage, ACL-verified IPC/PDF handoff, origin migration, index/history UX, approval archival, conflict/deletion semantics and hosted durable ciphertext relay are separate work.
